# 데이터와 연동 경계 제안

## 핵심 데이터

| 항목 | 제안 내용 |
| --- | --- |
| Inspection | 검수 ID, 기관 ID, 장비 ID, 생성 시각, 처리 버전 |
| ExpectedMedication | 기대 약품 코드·이름·규격·수량, 정보 출처 |
| CapturedImage | 이미지 ID, 촬영 시각, 제한된 조회 URL |
| AiResult | 분석 작업 ID, 모델 버전, 감지 결과, 점수, 처리 상태 |
| ReviewDecision | 작업자 결정, 사유, 담당자 ID, 서버 기록 시각 |
| AuditEvent | 대상 ID, 변경 전후 값, 담당자, 시각, 요청 ID |

이는 데이터베이스 확정 스키마가 아니다. 검수 단위와 장비가 제공하는 데이터에 따라 정한다. AI의 점수는 정의와 보정 여부를 확인하기 전까지 정확도 확률로 표현하지 않는다.

## 상태를 분리한다

- AI 처리: 대기 / 실행 중 / 완료 / 실패
- 작업자 검토: 미검토 / 검토 중 / 확인 필요 / 검토 완료
- 저장: 변경 없음 / 변경 있음 / 저장 중 / 저장됨 / 저장 실패

판정 종류(예: 일치·불일치·판독 불가)와 최종 출고 승인 여부는 실제 업무 규칙을 받은 뒤 정의한다. 장비 연결 끊김이나 AI 실패를 약품 불일치 판정으로 바꾸지 않는다.

## 제안 연동 흐름

1. 장비 또는 수집 서비스가 이미지와 작업 정보를 서버에 보낸다.
2. 서버가 분석 작업을 생성하고 AI 서비스 결과를 저장한다.
3. 웹앱은 API로 검수 목록과 상세를 조회한다.
4. 작업자가 검토 결과를 제출한다.
5. 서버가 기관·권한·버전을 확인하고 결과와 변경 이력을 함께 저장한다.

웹브라우저가 직접 데이터베이스나 장비 제어 권한을 갖는 구조는 기본안으로 삼지 않는다. 브라우저 카메라 촬영이 필요한지, 현장 전용 수집기가 필요한지는 장비 사양을 확인한 뒤 결정한다.

## API 설계 예시

- `GET /api/inspections`: 필터·페이지를 포함한 목록
- `GET /api/inspections/:id`: 기대 정보·이미지·AI 결과·검토 결과
- `POST /api/inspections/:id/reviews`: 검토 결과 저장
- `GET /api/medications`: 약품 검색
- `GET /api/devices`: 장비 상태
- `GET /api/audit-events`: 권한 범위 내 변경 이력

위 경로는 구현 전 제안이다. 실제 서버와 연결됐다는 의미가 아니다. 기관별 접근 제어는 서버에서 수행하며 화면에서 버튼을 숨기는 것으로 대신하지 않는다. 실제 데이터는 인증된 경로로 조회하고 데모 데이터와 분리한다.
